# Compliance & Legal Notes

## What this tool does

`market-radar-pl` reads **publicly visible listing pages** from Polish marketplaces
and tracks whether listings disappear — a signal potentially correlated with sales
or voluntary removal. It stores only data that any visitor would see in a browser.

## What this tool does NOT do

| Technique / capability      | Status   | Notes                                               |
|----------------------------|----------|-----------------------------------------------------|
| Anti-bot bypass            | NOT impl | No fingerprint spoofing, headless evasion, or TLS JA3 manipulation |
| Proxy / IP rotation        | NOT impl | Requests are rate-limited from the worker runtime   |
| CAPTCHA bypass             | NOT impl | If a CAPTCHA is encountered the request fails and is logged |
| Auto-contact to sellers    | NOT impl | No messaging, phone scraping, or email extraction   |
| Spam / bulk outreach       | NOT impl | Tool has no outbound communication capability       |
| Personal data collection   | NOT impl | Seller phone/email/name fields are not stored       |
| robots.txt enforcement     | NOT impl | Operators must verify source policy before enabling an adapter |

## Fetch safety and rate limiting

The worker enforces a per-domain delay (`FETCH_DELAY_SECONDS`, default 3 s).
Before a fetch, targets are validated to reject local/internal hostnames and
private/reserved network destinations. Redirect targets are validated again before
following them. This is a defense-in-depth SSRF boundary and does not replace an
explicit marketplace allowlist at ingestion time.

`FETCH_CONCURRENCY` is currently reserved configuration; the scheduler processes
watch URLs sequentially.

## Watch URL writes

`POST /api/watch-urls` is an administrative operation. Foundation v0 requires a
server-side bearer token and validates the requested source against a host allowlist.
For `manual` sources, permitted hosts must be configured explicitly.

Do not expose write credentials to browser JavaScript.

## Data stored

All stored data is drawn from publicly visible listing pages:

- Listing title
- Listing URL (public permalink)
- Price (PLN, as displayed)
- Category and location (as displayed)
- Thumbnail URL (public CDN link)
- Timestamps generated by this tool (first_seen_at, last_seen_at)

**No seller contact PII is intentionally collected.**

## "Probable exit" vs. "confirmed sale"

A listing disappearing from a page does **not** confirm it was sold. Possible reasons:

- Seller voluntarily removed it
- Platform moderation removed it
- Listing expired
- Temporary platform error
- Relisting under a different URL

The tool uses the label `probably_gone` with a `confidence` score (low/medium/high)
to communicate this uncertainty. It never asserts that a sale occurred.

Foundation v0 additionally distinguishes **authoritative** and **non-authoritative**
snapshots. Fetch errors, non-success HTTP responses, and unexpected empty snapshots
must not increment `missing_checks`.

## Robots.txt and Terms of Service

The current code does **not** implement automated `robots.txt` parsing or enforcement.
Before enabling a source adapter, operators are responsible for checking and complying
with the source Terms of Service, `robots.txt`, and applicable Polish/EU law.

## GDPR

Listing prices and descriptions posted publicly by sellers on a marketplace may
constitute personal data in some interpretations. Operators should:

1. Conduct a DPIA if processing at scale.
2. Apply data minimisation (store only what is needed).
3. Set appropriate retention limits.
4. Ensure the legal basis for processing is documented.

## Changes

Any addition of functionality that touches personal data, anti-bot techniques,
automated outreach, marketplace writes, or commerce automation must be reviewed
against this document before merging.
